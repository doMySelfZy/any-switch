# 技术设计：全局约束统一注入

## 1. 边界与总览

```
UI: RulesPage (文本框 + 目标勾选)
      │ invoke save_agent_rules { body, targets }
      ▼
commands/rules.rs  ── 校验标记 → 落库 → 计算写入目标并集 → 逐目标写文件
      │                                            │
      ▼                                            ▼
repo/rules.rs (agent_rules 单行表)        adapters/agent_rules.rs
      │                                    托管块 upsert / strip + 原子写 + 备份 + 锁
      ▼                                            │
sync_meta: agent_rules_applied_targets             ▼
                                          ~/.claude/CLAUDE.md
                                          ~/.codex/AGENTS.md
                                          ~/.pi/agent/AGENTS.md
                                          ~/.prime/agent/AGENTS.md
```

不复用 `target_bindings` / `apply_records`：那是「站点 → 目标」的应用状态机（含密钥指纹、孤儿判定、`restore_official`），与全局约束无关。约束的「已应用目标」用 `sync_meta` 记录，与 MCP 同一套做法。

## 2. 数据模型

### 2.1 表 `agent_rules`（单行）

```sql
CREATE TABLE IF NOT EXISTS agent_rules (
  id INTEGER PRIMARY KEY CHECK (id = 1),
  body TEXT NOT NULL DEFAULT '',
  targets_json TEXT NOT NULL DEFAULT '[]',
  updated_at INTEGER NOT NULL DEFAULT 0
);
```

- 单行（`id = 1`），与 `settings` 表同构；首次读取时无行 → 返回空正文 + 空目标的默认值，不预插行。
- `targets_json` 存 `Vec<TargetKind>`，serde 序列化为 `["claude_code","codex"]`。
- 空正文 **或** 空目标集合 = 「不生效」：两个条件任一成立就按清理处理。

### 2.2 迁移

- `SCHEMA_VERSION` 2 → 3。
- 表进 `V1_SCHEMA`（新库）**且**加 `ensure_agent_rules_schema()` 到 `ensure_incremental_schema()`（存量库）。该函数已在 `apply_schema` 的三个「库已存在」分支全部调用（`src-tauri/src/db/migrate.rs:215-238`），所以版本落后分支与 legacy 分支都能拿到新表。
- 回归测试照抄 `v1_database_reaches_current_schema_with_mcp_table` 与 `legacy_database_keeps_newapi_columns_and_gains_mcp_table`（`src-tauri/src/db/migrate.rs:942-1006`）两个用例，断言 `agent_rules` 存在。

### 2.3 同步

- `FINGERPRINT_TABLES`（`src-tauri/src/sync.rs:41`）加入 `"agent_rules"`，8 → 9 项。回归测试照抄 `sync.rs:652-670` 的 MCP 用例：改 `agent_rules` 行 → 指纹变化。
- 约束正文是普通业务数据，随既有备份 / WebDAV 同步；不额外加密（用户自己写的内容不是密钥），UI 明示它会被写到明文文件。

## 3. 托管块协议（adapters/agent_rules.rs）

### 3.1 标记

```
<!-- xiaobai-switch:begin global-rules -->
<!-- Generated by XiaoBaiSwitch Plus · 由 XiaoBaiSwitch Plus 生成，请勿在此块内手工编辑 -->
<用户正文>
<!-- xiaobai-switch:end global-rules -->
```

- 用 HTML 注释：在 Markdown 渲染中不可见，同时是纯文本行，便于人肉定位与 grep。
- 提示行是**固定双语**而非走 i18n：它写在目标文件里（可能跨语言切换后残留），不是 UI 文案。这是 i18n 约定的有意例外，在代码注释里写明。
- 前缀 `xiaobai-switch:` 与既有 `xiaobai_` 命名空间同源。

### 3.2 纯函数（单测主战场）

| 函数 | 契约 |
|------|------|
| `validate_body(&str) -> AppResult<()>` | 正文含标记字面量 → `validation_failed` 并指出是哪一处 |
| `render_block(&str) -> String` | 拼出完整托管块，正文末尾补 `\n` |
| `strip_blocks(&str) -> AppResult<(String, usize)>` | 删除全部托管块并返回剩余正文；出现 BEGIN 但之后没有 END → `invalid_config` 错误；END 单独出现（无 BEGIN）不报错，按用户内容原样保留 |
| `upsert_block(text, Option<&str>) -> AppResult<Option<String>>` | `Some(block)`：先 strip 再在末尾追加一个块；`None`：只 strip。返回 `None` 表示无需写盘 |
| `should_delete(text) -> bool` | 剩余内容去掉换行后全为空白 → true |

### 3.3 字节保真规则

- **BOM**：读取时识别 `EF BB BF` 并记录，写回时原样加回；新建文件不加 BOM。
- **追加分隔**：正文末尾不是 `\n` → 补 `\n\n`；正好一个 `\n` → 补 `\n`；已有 ≥2 个 `\n` → 直接追加。保证与用户内容之间恰好一个空行。
- **删除后的收尾**：删掉托管块后对剩余内容 `trim_end_matches(['\n','\r'])`；非空则补恰好一个 `\n`。**代价**：用户文件原本若以多个空行结尾，清理后会归一为一个换行。这是唯一允许的字节变化，写进 PRD 的 R2.3 说明。文件里本来就没有托管块时直接返回「无变化」，连这个归一都不做。块位于文件中段（用户手工搬动过）时只忠实移除块本身，内部空行原样保留。
- **幂等**：同一正文连续保存两次，第二次 `upsert_block` 结果与第一次逐字节相同（有专门单测）。
- **多处块收敛**：文件里出现 2 个以上托管块（异常/手工复制）时全部删除后重写一个，不报错。

### 3.4 失败姿态

| 情况 | 行为 |
|------|------|
| 路径是目录 | `invalid_config` 错误，不写 |
| 文件不是合法 UTF-8 | `invalid_config` 错误，不写 |
| BEGIN 无 END | `invalid_config` 错误，不写 |
| 读取失败（权限等） | 原样报错，不写 |
| 无需变更（无块可写、文件里也没有块） | 直接返回 `changed: false`，**不备份、不写、不触碰文件** |
| 某目标写失败 | 该目标 `ok: false` + 错误消息，其他目标继续；失败目标留在 `sync_meta` 里，下次重试 |

## 4. 路径解析

| 目标 | 解析 | 备注 |
|------|------|------|
| Claude Code | `claude_rules_path(override)`：override → `CLAUDE_CONFIG_DIR` → `~/.claude`，再 join `CLAUDE.md` | 与 `claude_mcp_json_path`（`paths.rs:479-494`）同一套优先级；新增独立函数，**不动** `resolve_claude_home`（其 `CLAUDE_CONFIG_DIR` 盲区是既有问题，另开任务） |
| Codex | `resolve_codex_home(override)` + `AGENTS.md` | 另查 `<codex_home>/AGENTS.override.md` 是否存在，仅用于 UI 警告 |
| Pi | `resolve_pi_agent_dir(override)` → 目录内选文件 | 见下 |
| Prime | `resolve_prime_agent_dir(override)` → 目录内选文件 | 同 Pi |

Pi/Prime 选文件规则（R5.2）：

```
AGENTS.md 存在        → AGENTS.md
否则 CLAUDE.md 存在   → CLAUDE.md
否则                  → AGENTS.md（新建）
```

理由：两个 CLI 的同目录优先级是 `AGENTS.override.md > AGENTS.md > CLAUDE.md`。如果用户只有手写的 `CLAUDE.md`，我们新建 `AGENTS.md` 会让它**整体压过**用户自己的文件——等于把用户内容静默降级。所以有 `CLAUDE.md` 就追加到它里面。

`atomic_write` 与 `FileLock` 都会 `create_dir_all(parent)`（`atomic.rs:10-12,93-95`），所以目标 CLI 没装也不会报错，只是目录被建出来。

## 5. 命令层契约（commands/rules.rs）

```rust
// 读取当前约束（无行时返回默认值）
#[tauri::command] pub fn get_agent_rules(state) -> AppResult<AgentRules>;

// 保存并立即应用；返回逐目标结果
#[tauri::command] pub fn save_agent_rules(state, body: String, targets: Vec<TargetKind>)
    -> AppResult<AgentRulesApplyResult>;

// 四个目标的落点路径 + 存在状态 + Codex 遮蔽警告
#[tauri::command] pub fn agent_rules_target_paths(state)
    -> AppResult<Vec<AgentRulesTargetPath>>;
```

DTO（`domain/rules.rs`，全部 `#[serde(rename_all = "camelCase")]`）：

```rust
pub struct AgentRules { pub body: String, pub targets: Vec<TargetKind>, pub updated_at: i64 }
pub struct AgentRulesTargetPath {
    pub target: TargetKind,
    pub path: String,
    pub exists: bool,
    pub shadowed_by: Option<String>,   // 仅 Codex：AGENTS.override.md 的路径
}
pub struct AgentRulesTargetResult {
    pub target: TargetKind, pub ok: bool, pub path: String,
    pub changed: bool, pub backup_paths: Vec<String>, pub message: String,
}
pub struct AgentRulesApplyResult { pub results: Vec<AgentRulesTargetResult>, pub applied_at: i64 }
```

`save_agent_rules` 流程：

1. `validate_body`（含标记 → 直接报错，不落库）。
2. 归一化目标集合（去重）；落库 `body` / `targets` / `updated_at`。
3. `desired = if body.trim().is_empty() { vec![] } else { targets }`。
4. `union = desired ∪ sync_meta["agent_rules_applied_targets"]`（本次请求之外的旧目标也要走一遍以清理）。
5. 逐目标：`desired.contains(target)` → `upsert_block(text, Some(render_block(body)))`；否则 → `upsert_block(text, None)`。
6. 写成功且 `changed` → 备份 + `atomic_write`；剩余内容为空白 → `fs::remove_file`（文件不存在则跳过）。
7. 记录 `sync_meta`：写失败的目标 ∪ 仍在 `desired` 里的目标（与 MCP 的 `targets_to_record` 同语义，`commands/mcp.rs:220-233`）。
8. 备份根：`backups_dir()?/agent-rules/`（对齐 MCP 的 `backups_dir()?/mcp`）。

## 7. 权衡记录

- **单条 vs 多条**：用户明确选单条文本框（见 PRD OQ1 结论）。单条模型下 `agent_rules` 是单行表；若以后要扩成多条，迁移路径是把单行升级为带 `sort_order` 的多行表 + 编辑页改成列表，适配器层（按目标拼一个块）无需改动——这是当前设计的可演进点。
- **托管块 vs 独立文件**：不采用「整文件归我们所有」。因为 Claude Code 只认 `CLAUDE.md` 这一个路径，Codex 只认 `AGENTS.md`，四者都是单文件槽位，独占会直接覆盖用户已有内容。
- **不写 `AGENTS.override.md`**：它是 Codex 文档里的临时覆盖文件，占用它等于长期劫持优先级；只警告。
- **不加应用启动时的自动重写**：MCP 也不做。只有保存与手动「应用」触发写盘，避免每次启动都去碰客户端文件。

## 8. 风险与回滚

| 风险 | 缓解 |
|------|------|
| 误删用户文件 | 只有「删除托管块后剩余内容全为空白」才删文件；其余情况保留 |
| 写坏用户内容 | 每次写前 `backup_file` 到 `~/.xiaobai-switch/backups/agent-rules/`；`atomic_write` 原子替换 |
| 与客户端并发写同一文件 | `<文件名>.lock` 目录互斥（与 Pi/Prime 适配器同一约定） |
| 存量库升级丢表 | `ensure_incremental_schema` 覆盖三个分支 + 回归测试 |
| 改动被其他会话带偏 | 本任务只碰新增文件与 5 处注册点（`migrate.rs` / `db/mod.rs` / `sync.rs` / `lib.rs` / `commands/mod.rs`），与在跑的 `09-13-local-proxy` 任务无文件重叠 |

回滚：删掉新增文件、回退 5 处注册点、把 `SCHEMA_VERSION` 退回 2（表残留无害）。已写入目标文件的托管块由用户在 UI 里清空正文并保存即可移除，或手工删块；`backups/agent-rules/` 里有每次写入前的原件。
